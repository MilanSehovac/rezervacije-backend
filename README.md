# rezervacije-backend
Backend for Booking Web App that helps customers of and barbers, makeup/nails artists, hairstylists etc. by handling the booking process. These businesses have a problem with full inboxes of reservations, having to dot them down in notebooks and such often leads to mistakes and forgotten reservations/unopened messages.


## Scheduling model (active / passive time)

A service is an ordered list of **phases**, e.g. `30 min active -> 60 min passive -> 30 min active`
(`salon_services.phases`, falls back to `activeDuration` + `passiveDuration`).

* **Active** phase: a staff member works on the customer. Active phases of the same staff member never overlap.
* **Passive** phase (colour developing, mask, ...): staff is free. Any number of other bookings may use that time,
  as long as *their* active phases fall into it. Set `canOverlap = false` on a service to block the staff for its whole duration.
* **Seats** (`salons.seats`, `null` = unlimited) are occupied for the whole service (active + passive).
* `requiredStaff > 1` needs that many free staff during every active phase. A salon without team members has one implicit staff member.
* A booking stores a snapshot (`bookings.schedule`) of phases and assigned staff, so editing a service never moves existing bookings.
* Booking creation locks the salon row in a transaction, so concurrent requests cannot take the same gap.

Engine: `src/services/scheduler.js` (pure functions). Tests: `npm test` (the e2e test creates and drops a `reservations_test` database).

## Environment

`DB_*`, `PORT`, `REFRESH_TOKEN_SECRET`, `CLIENT_ORIGIN` (CORS), `AUTO_APPROVE_SALONS=true` (skip manual approval of new salons; there is no admin UI yet).

## SEO and deployment notes

* `GET /robots.txt` and `GET /sitemap.xml` are generated by the API (approved salons only, canonical `/salon/<id>-<slug>` URLs).
  Route both paths of the **public site domain** to the API in your reverse proxy (the Vite dev server already proxies them).
* Set `PUBLIC_SITE_URL` (e.g. `https://beautybook.example`) so the sitemap and robots file contain absolute URLs.
  The frontend reads `VITE_SITE_URL` (defaults to the current origin) for canonical links and structured data.
* The frontend is a single-page app: Google renders it, but link previews (WhatsApp, Facebook) only see the static tags from `index.html`.
  If rich previews for salon pages matter, serve the built app through a small server-side step that fills `<title>` and Open Graph tags per salon.

## Booking management

* Salon rules: `autoConfirm`, `minNoticeHours`, `cancellationHours` (customers cannot cancel or move inside that window; owners can).
* Customers can move a booking (`PATCH /bookings/:id/reschedule`), the engine ignores the booking being moved. A confirmed booking that moves goes back to pending unless the salon confirms automatically.
* Owners can add walk-in / phone bookings (`POST /bookings/salon/manual`) and block time (`/salon/me/blocked`): lunch, days off, holidays, for one team member or the whole salon.
* A customer cannot hold two overlapping bookings, and bookings are limited to 180 days ahead.
* Accounts: `POST /users/me/password`, `DELETE /users/me` (soft delete; upcoming bookings are cancelled, a salon is unpublished).
